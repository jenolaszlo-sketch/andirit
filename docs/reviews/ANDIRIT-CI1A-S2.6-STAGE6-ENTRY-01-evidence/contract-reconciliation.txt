259: ### D.4 — Index maintenance, publication and cancellation: **D4 ACCEPTED WITH EXPLICIT INVARIANTS**
260: 
261: Select a bounded, publication-consistent occurrence-index model. The
262: independently verified R2/Q3 index-freshness behaviour forms the experimental
263: basis.
264: 
265: **Required invariants:**
266: 
267: 1. A query may use only an index consistent with the accepted published
268:    occurrence-fact generation.
269: 2. A stale, unbound or unverifiable derived index must refuse with an explicit
270:    status.
271: 3. A stale index must not silently trigger an unbounded full-store scan.
272: 4. Failed staging must preserve the last accepted publication and corresponding
273:    valid index state.
274: 5. Cancelled staging must not expose partial facts or index entries.
275: 6. Superseded publication must not replace a newer accepted generation.
276: 7. Rebuild/reopen must produce a semantically equivalent published index.
277: 8. Contributor changes and scoped deletion must update publication and index
278:    visibility consistently.
279: 9. Bounded queries must have deterministic ordering and explicit result limits.
280: 10. Query behaviour during concurrent publication must follow a defined snapshot
281:     or freshness contract.
282: 
283: **Maintenance policy (preferred simple model):**
284: 
285: - Build or update the index within the accepted publication lifecycle.
286: - Make the index valid only when its publication identity is corroborated.
287: - Refuse stale or inconsistent state.
288: - Permit explicit bounded reconstruction where necessary.
289: - Verify reconstructed state before allowing normal queries.
290: 
291: Do **not** introduce a general background maintenance service, a distributed
292: index coordinator, or an automatic repair framework without demonstrated need. Do
293: **not** invent additional concurrency guarantees beyond Q3's evidence.
294: 
295: **D4 implementation qualification:** CI-1A must reproduce the applicable
296: stale-index, cancellation, failed-publication, supersession and reopen tests
297: **using actual production storage and APIs**. The previous in-process experiment
298: does not establish native or cross-process atomicity; record those limits
299: explicitly.

EXCERPT: S2.5 entry assessment — native versus compatibility environment rule
SOURCE: docs/reviews/ANDIRIT-CI1A-S2.5-ENTRY-ASSESS-01.md lines 124-126
----------------------------------------------------------------------------------------------------
124: **Native vs compatibility environments.** `ubuntu-latest` is a genuine Linux host (hosted VM); its logs are the evidence class the matrix names ("CI pipeline logs"). WSL2, Docker-on-Windows, or other Windows-hosted compatibility environments are **not** native Linux execution; the accepted requirement does not explicitly allow them, so a WSL2 result must not be presented as SQ-05 closure without an owner amendment. The S2.2-era qualification "hosted CI is not independent cross-platform qualification" remains binding as an independence statement: hosted logs require independent reviewer verification of SHA-binding and completeness; a reviewer-controlled native Linux execution would be stronger.
125: 
126: **Path.** Owner-authorized publication of a reviewed commit to `origin` (push or PR) → ubuntu-latest CI run bound to that SHA → suite logs; **or** an owner-provided native Linux host/VM under reviewer control executing the suite. Either route is a bounded owner decision (push authorization or runner provision). What can be reused from Windows: test definitions, expected semantics, and the reviewed SHA only — **no Windows result counts as Linux evidence**. What must be executed independently on Linux: the actual test execution (locking/WAL/mmap/path/persistence/reopen/publication/recovery/authority behavior as covered by the suite) plus the behavior matrix.
