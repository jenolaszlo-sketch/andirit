# Windows checkout and exact-byte formatting

On SDK 10.0.401, `dotnet format Andirit.slnx --no-restore --verify-no-changes` exits **0** with the Windows checkout conversion profile and **2** with exact Git blobs. The latter requests CRLF in seven whitespace edits limited to `src/Andirit.CSharp/CSharpProjectDiscovery.cs` (lines 304–305) and `src/Andirit.CSharp/VerifiedCSharpCompilation.cs` (lines 110–114). Those are the comment-adjacent continuation breaks in a constructor expression and an `if` predicate. Roslyn's whitespace pass regenerates those breaks using its Windows newline setting when no explicit end-of-line option is supplied. It leaves other existing newlines alone in this invocation. [Checkout log](gates-final/checkout-format.log) · [Exact-byte log](gates-final/format.log)

Both files are committed LF. The canonical checkout has CRLF under system `core.autocrlf=true`. Neither file has an applicable `.gitattributes` rule, and the root `.editorconfig` declares no `end_of_line`. The exact export disabled the Git conversion per command, and the checkout-profile export enabled it. These are the same seven requests as the independently reported R2 failure. Both files predate R3 and have unchanged blob bytes, as do the Git and formatter configuration files. [Line-ending provenance](gates/line-ending-provenance.log) · [QUAL-03 exact-byte format receipt](../CI1A-S2.5-WP-S25-4-QUAL-03-evidence/gates/format.log)

WP-S23-3 publication integration §5.7 requires `dotnet format Andirit.slnx --verify-no-changes` exit 0. R3 also explicitly governs both profiles. A separately authorized narrow resolution is to trial an explicit LF formatter setting scoped to these two files, verify the same exact blobs and checkout-profile behavior, then review the smallest consistent line-ending policy if the profiles still differ.
